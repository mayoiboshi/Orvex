# Orvex 2.0 产品愿景

更新日期：2026-11-06。本文记录长期方向和完整功能构想，不是开发授权、交付承诺或已确认的技术方案。实际完成度、阶段优先级和下一步目标统一维护在 [ROADMAP](ROADMAP.md)；当前实现见 [ARCHITECTURE](ARCHITECTURE.md)，已采用的技术选择见 [DECISIONS](DECISIONS.md)。

## 我们要做的产品

打造一个界面精美、播放体验优秀、媒体来源丰富、管理方便、可高度个性化的个人娱乐播放中心。

以 Flutter 为主要技术路线，长期覆盖 iOS、Android、macOS、Windows；iPhone 和 iPad 分别适配。当前交付仍优先 iOS/iPadOS，长期平台目标不意味着本轮扩展平台工作。

用户应能方便地找到想看的内容，清楚地选择播放版本、字幕和音轨，顺畅地观看，并在下次打开时继续。增加数据源或下载能力，应让这个过程更方便，不让基础播放变复杂。

## 体验原则

1. **体验优先于数量。** 优先解决导入、打开、拖动、字幕、声音和续播的问题，再增加功能入口。
2. **共享逻辑，适配平台。** 四个平台尽可能复用业务逻辑；允许手机触控、平板布局、桌面窗口与键鼠操作采用不同交互和 UI。
3. **先播放，再扩展。** 先完善本地播放，再逐步扩展媒体库、数据源和下载；现有媒体库能力可以继续改进，不要求阶段机械串行。
4. **精美且可控。** 保持首页、海报、详情和播放控制的一致性，动画服务于操作反馈；逐步支持播放偏好、界面和画质的个性化，不把全部选项堆到播放器上。
5. **私人内容由用户掌握。** 后续数据源、隐私内容和同步功能需要明确保存位置、访问边界与可见性；具体隐私保护方案待调研。
6. **小步交付。** 沿用 S/M/L 分级，不引入额外项目管理工具，不要求所有小任务写设计文档。
7. **构想与方案分开。** 下列内容都是产品方向；未确定的技术实现均为「待调研」。列入规划不代表批准实现，也不代表全部必做或已有排期。

## 阶段一：本地播放体验

目标：用自己的文件稳定地完成导入、观看、切换字幕/音轨和继续观看。

| 功能构想 | 希望获得的体验 / 规划边界 |
| --- | --- |
| 本地视频导入与文件管理 | 导入和重新打开可靠，逐步完善文件整理、删除、副本及空间管理；具体管理方式待设计 |
| 播放器基础功能、控制栏、进度拖动 | 播放/暂停、跳转和全屏反馈清楚，横竖屏与控制栏不妨碍观看 |
| 音量、亮度及播放手势 | 调节自然、避免误触；各平台系统能力和手势方案待调研 |
| 字幕、音轨及播放设置 | 易于选择和调整，逐步完善外挂字幕管理与偏好恢复 |
| 格式兼容、播放记录、稳定性 | 按实际容器/编码/字幕样本记录结果，错误可理解，历史和续播可靠；不承诺支持所有格式 |
| iPhone、iPad、Android、Windows、macOS 适配验证 | 分别检查触控、键鼠、布局、声音和系统行为；按实际设备证据推进 |

## 阶段二：媒体库

目标：从「打开文件」走向「方便地找到、认识和整理内容」。

| 功能构想 | 希望获得的体验 / 规划边界 |
| --- | --- |
| 首页、海报墙、详情页与动画 | 围绕真实媒体、继续观看和资料组织内容，保持布局与转场一致 |
| 影视元数据刮削与系列归档 | 识别影片和番剧，允许纠错，逐步支持系列、季度、分集归档；其他元数据来源及归档模型待调研 |
| 搜索、筛选、收藏、继续观看 | 快速缩小范围，保存个人偏好，清楚展示观看进度 |
| 本地媒体与远程媒体统一管理 | 尽量统一浏览和观看记录，同时明确来源、离线可用性及失效状态；身份与同步方案待调研 |

## 阶段三：多数据源聚合

目标：在一致的浏览和播放体验中使用自己的多种媒体来源。

| 功能构想 | 研究范围 / 尚未确定的部分 |
| --- | --- |
| NAS、WebDAV、SMB | 连接、认证、目录浏览、播放与连接失效恢复；客户端依赖和平台文件访问方式待调研 |
| Emby、Jellyfin | 资料、媒体版本、播放地址及观看状态的衔接；接入范围与认证方案待调研 |
| TVBox 类数据源及插件适配 | 数据格式、解析方式、插件兼容范围、维护成本及平台可行性待调研；不预先搭建通用插件框架 |
| 可扩展的第三方及合法成人内容数据源 | 保留接入构想；具体来源、接口授权、扩展方式与平台可用性待调研，未选定供应方 |
| 私人媒体库与隐私保护 | 研究来源凭据保存、敏感内容的显示与搜索控制、设备访问保护；不把规划写成已有保护能力 |

## 阶段四：下载中心

目标：下载过程清楚、可恢复，下载后的内容方便管理和播放。

| 功能构想 | 候选方向 / 尚未确定的部分 |
| --- | --- |
| 内置 HTTP/HTTPS 下载、断点续传 | 作为基础下载方向；恢复校验、存储和后台策略待调研 |
| HLS/DASH 离线下载 | 清单、分片、音轨/字幕与离线播放适配待调研 |
| 内置磁力链与 Torrent 下载 | **libtorrent 为候选，待调研**；尚未决定依赖、原生集成方式及各平台可行性 |
| 迅雷下载 SDK | 仅作为可选 HTTP 加速后端构想；SDK 可获得性、授权、平台覆盖及接口能力待调研，不作为默认后端 |
| 迅雷云盘离线接入 | 可行性研究；官方接口、授权方式及实际可用能力待调研，与下载 SDK 分开评估 |
| NAS、aria2、qBittorrent 远程下载 | 研究把任务交给远程设备及查看状态；不等同于本机内置下载 |
| 下载进度、任务队列、失败恢复、边下边播 | 逐步设计排队、暂停/恢复、错误重试和空间管理；边下边播的格式与后端限制待调研，不承诺所有下载方式都支持 |

内置与远程下载分别评估，再决定是否共享任务展示。移动端后台、磁盘占用和平台分发条件应在选型时核验；当前没有下载系统技术决策。

## 阶段五：高级影音体验

目标：在基础播放稳定后，为有需求的用户提供可选增强能力。

| 功能构想 | 研究范围 / 尚未确定的部分 |
| --- | --- |
| AI 字幕识别、翻译与外挂字幕管理 | 识别与翻译质量、时间轴、文件关联、本地/云端处理、隐私与成本待调研；未选模型或服务 |
| 弹幕与字幕避让 | 来源、同步、密度与遮挡控制待调研，保持字幕和画面可读 |
| MPV Shader、画质预设、GPU-Next | 播放器接口、渲染兼容、设备性能和功耗待调研；当前使用 libmpv 不代表已支持这些能力 |
| AI 补帧 RIFE | 仅为可行性研究；实时性能、延迟、发热及各平台加速路径待调研 |
| 多设备同步播放、一起看 | 远期构想；会话、进度同步、延迟补偿、连接方式与隐私边界待调研，未决定服务器方案 |

## 怎样长期维护

- 本文维护愿景、体验原则与功能范围，不复制完成状态表；ROADMAP 维护状态、优先级和近期目标，验证记录保留证据。
- 每次只从规划中选择一个明确、可验证的小目标。阶段顺序表示依赖与方向，不设固定日期，也不自动生成开发任务。
- 重大范围或技术选择发生变化时更新相应文档；只有正式采用的方案才写入 DECISIONS。普通小修复不新增流程或必写设计文档。
- 本轮仅建立规划；未研究外部 SDK、服务或模型的最新可用性，表中候选名称不构成选型推荐。
